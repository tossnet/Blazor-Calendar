# Contributing to Blazor-Calendar

Thanks for your interest in contributing! Please read this document before opening a pull request.

## Discuss before implementing

Before implementing a feature, a behavior change, or a non-trivial bug fix:

1. Search existing issues. Create an issue if none covers the problem, or join an existing issue instead of creating a duplicate.
2. Describe the problem, the expected benefit, and your proposed approach. Comment on an existing issue if you intend to work on it; you do not need to be its author.
3. Wait for the maintainer to agree that the change and proposed approach fit the project before starting implementation. Opening an issue alone is not approval.
4. Link the issue containing that agreement in the pull request's **Issues** section, using `Fixes #1234` when the pull request resolves the issue.

This discussion helps avoid spending time on changes that do not fit the project's goals or design. Agreement to start implementation does not guarantee that the pull request will be accepted; normal review and testing requirements still apply.

Prior discussion is not required for small documentation-only corrections (such as spelling, grammar, or broken links), trivial bug fixes with an obvious solution and no API or intended behavior change, or automated dependency update pull requests. Explain the applicable exception in the pull request's **Issues** section. If you are unsure whether an exception applies, discuss the change in an issue first.

Pull requests opened without prior agreement may be closed without review.

## One change per pull request

Keep each pull request focused on a single issue. Please do not open several pull requests in a row before the previous ones have been reviewed: the maintainer reviews contributions on their own time.

## AI contribution policy

AI-assisted contributions are welcome. Fully AI-generated or autonomous pull requests without meaningful human review are not accepted.

Before submitting any pull request, whether or not AI tools were used, a human contributor must:

- Personally review all changes and understand how they work and affect the project.
- Test the changes and describe the validation performed in the pull request's **Test Plan**, including any tests that could not be run.
- Take responsibility for the contribution's correctness, quality, licensing, and compliance with this project's guidelines.

AI tools do not replace human judgment or transfer responsibility to the maintainer. For automated pull requests, a human must perform this review and complete the declarations; there is no automatic exemption for bots.

## Pull request declarations

Complete every checkbox in the pull request template's **Issue discussion declaration** and **AI contribution declaration** sections. The **PR declarations** workflow check fails if a declaration is missing or unchecked, and runs again when the pull request description or commits change. The repository owner and collaborators are exempt.

This check verifies the declarations only; it does not verify issue links, maintainer agreement, whether an exception applies, whether code was generated by AI, or whether a human actually reviewed it. The maintainer validates these during review and may reject contributions that do not meet this policy even when the check passes.

## Submitting a pull request

- Rebase your branch on `main` before submitting.
- Build the solution and run the samples to validate your changes.
- Update the README when you add or change a public parameter.
